# security-audit

Один скилл на все проекты. Источники: сканер vibe-audit (ika.explains, MIT), ТЗ на аудит веб-приложения и методика «проверять запуском, а не чтением». Сканер переписан и проверен тестами на реальных репозиториях.

## Принципы (почему именно так)

1. **Проверять запуском, а не чтением.** Чтение кода находит защиту, которой нет, но не находит защиту, которая есть и не работает. Два реальных случая. Лимитер «5 запросов в час» определял отправителя по заголовку, который тот присылает сам, — 7 запросов с разными значениями прошли все. CSP выглядела прилично, но не гасила инлайновый `onerror`, и это выяснилось только в браузере. Поэтому статус «Защищено» ставится только при наблюдаемом результате: код ответа, строка лога, сообщение консоли. Не удалось проверить — пиши в «Не проверено», не додумывай.
2. **Только свои ресурсы и только локально.** Во время аудита никаких запросов к продакшну и чужим серверам. Исключение одно — `livecheck.py` (пассивные GET к своему домену), только по явной просьбе и с подтверждением владения.
3. **Безвредные маркеры, никаких боевых payload'ов.** Тестовые данные: `<b>audit-marker</b>`, `'`, `"`, `<`, `>`, `&`. Единственный исполняемый маркер — проверка CSP в `references/dynamic-testing.md`: он только пишет строку в консоль на localhost. Работаешь по схеме «проблема → фикс»: не объясняешь, как эксплуатировать, и не пишешь эксплойты.
4. **Секреты не цитировать.** Показывай их только маскированно (`sk-pro…Qw`). Если найден живой ключ, первая строка ответа: «перевыпусти его сейчас».
5. **Сначала отчёт, код не менять без подтверждения.** Это касается и тестов с CI из этапа 5: их предлагаешь, делаешь после «да».
6. **Каждое утверждение подкрепляется `файл:строка` и фрагментом кода**, а для динамики — командой и наблюдаемым результатом.
7. **Трассируй поток данных от источника до места использования.** Если данные на пути гарантированно не контролируются пользователем, это не уязвимость. Находки сканера — кандидаты, а не вердикты: каждую подтверди или отклони.
8. **Фиксируй то, что уже защищено хорошо** — с механизмом и местом в коде, чтобы при рефакторинге это не сломали.

## Выбор режима

| Запрос | Режим |
|---|---|
| «проверь перед деплоем», «быстро глянь», «нет ли ключей в коде» | Быстрая проверка |
| «аудит безопасности», «полный аудит», «security review»; проект с деньгами, персональными данными или админкой | Полный аудит |

Если непонятно, какой режим нужен, начни с быстрой проверки. Для проектов с деньгами или персданными в конце предложи полный аудит.

## Быстрая проверка

1. Запусти сканер (раздел «Сканер» ниже).
2. Каждую 🔴 и 🟡 находку открой в коде и проследи поток данных: подтверди или отклони. 🔵 — пробегись и отметь важное.
3. Пройди `checklist.md` вместе с пользователем: там то, что сканер не видит.
4. Ответ: одна строка «N находок: X критичных / Y важных / Z на проверку», затем топ-3 «чини сейчас» с `файл:строка` и готовым фиксом. Отклонённые кандидаты перечисли одной строкой с причиной.

## Полный аудит

Работай по этапам по порядку. Результат — `SECURITY_AUDIT_REPORT.md` в корне проекта.

### Этап 0. Разведка — первым делом
Составь для отчёта:
1. **Стек:** язык, фреймворк и версия (для Next.js — App или Pages Router), БД, ORM/драйвер, аутентификация, хостинг, почтовый сервис, внешние API.
2. **Точки ввода (sources):** формы, API routes, server actions, route handlers, query- и path-параметры, заголовки, cookies, вебхуки, загрузка файлов, импорт, данные из внешних API.
3. **Места вывода (sinks):** публичные страницы, админка/CRM, письма, уведомления (Telegram и т.п.), экспорт CSV/Excel/PDF, логи, метаданные (`<title>`, OpenGraph, JSON-LD).
4. **Хранилища:** где данные сохраняются и откуда потом читаются и выводятся.
5. **Роли и доступы:** гость, пользователь, исполнитель, админ — какие маршруты кому доступны.

Затем по стеку подгрузи справочники (читай только нужные):

| Признак в проекте | Справочник |
|---|---|
| `next` в package.json | `references/stacks/nextjs.md` |
| `@supabase/*`, папка `supabase/` | `references/stacks/supabase.md` |
| netlify.toml, wrangler, vercel.json, Cloudflare перед сайтом | `references/stacks/hosting.md` |
| платежи, escrow, выплаты, баланс, вебхуки платёжек | `references/stacks/payments.md` |
| отправка писем, уведомления в Telegram/Slack | `references/stacks/email-notifications.md` |
| Django / Flask / FastAPI | `references/stacks/python.md` |
| Java / Kotlin / Scala (Spring, Play, http4s) | `references/stacks/jvm.md` |

### Этап 1. Автоматика
Запусти сканер и аудит зависимостей. Результат этапа — список кандидатов для этапов 2–3.

### Этап 2. Ручной проход по чек-листу
`references/audit-checklist.md` — 15 разделов, в каждом написано, что искать и какая защита считается достаточной. Каждому разделу ставишь статус: **найдена проблема / защищено / неприменимо** (с обоснованием: такой функциональности нет) / **не проверено** (с причиной). Отдельно и обязательно проверь админку/CRM, email-шаблоны, уведомления и экспорт как места stored XSS: бот оставляет вредоносный ввод в форме, а срабатывает он у владельца.

### Этап 3. Проверка запуском
`references/dynamic-testing.md` — рецепты. Если среда позволяет (Claude Code, терминал с проектом): поставь зависимости, подними проект локально с тестовыми ключами, отправляй настоящие запросы с маркерами, открой браузерную часть и смотри консоль. Каждую проверку фиксируй так: команда → наблюдаемый результат → вывод. Если запустить нельзя (например, в чате без кода проекта), всё непроверенное запуском уходит в «Не проверено», а пользователю отдаёшь готовые команды для самопроверки.

### Этап 4. Риск и отчёт
Методика и шаблон — в `references/risk-and-report.md`, заготовка файла — `assets/report-template.md`. Риск = вероятность (1–5) × влияние (1–5): 20–25 критический, 12–19 высокий, 6–11 средний, 1–5 низкий. Если защита полная, находка идёт в раздел «Защищено», а не в список уязвимостей.

### Этап 5. Что оставить после себя — после подтверждения
`references/hardening.md`. Отчёт описывает один день, а защита должна не развалиться молча:
1. Автотест на каждую проверяемую находку. Критерий один: тест падает, если защиту убрали.
2. CI на каждое изменение: линтер, типы, тесты, аудит зависимостей. Отдельно проверь, что сборка на хостинге не запускает тесты — это типичная ловушка.
3. Автоматическое слежение за зависимостями. Оповещения часто молчат, пока не включён граф зависимостей.
4. В файл инструкций проекта (CLAUDE.md / AGENTS.md) записать, какие данные доверенные и почему.

Предложи это после отчёта списком и делай только после согласия.

### Критерии готовности
- [ ] Этап 0 выполнен, карта ввода/вывода есть в отчёте.
- [ ] Каждый раздел чек-листа отмечен статусом, «неприменимо» обосновано.
- [ ] У каждой находки есть `файл:строка`, поток данных, риск, конкретное исправление и способ проверить исправление.
- [ ] Админка/CRM, письма, уведомления и экспорт проверены как места stored XSS.
- [ ] Каждое «Защищено» подкреплено наблюдаемым результатом, иначе перенесено в «Не проверено».
- [ ] `SECURITY_AUDIT_REPORT.md` сохранён. Код не менялся без подтверждения.

## Сканер

```bash
python3 <папка-скилла>/scripts/audit.py /путь/к/проекту
python3 <папка-скилла>/scripts/audit.py . --json findings.json --fail-on critical   # для CI
```
На Windows вместо `python3` используй `python` или `py`. Папка скилла в Claude Code — обычно `~/.claude/skills/security-audit`. Нужен Python 3.9+, внешних зависимостей нет. Сканер только читает: git вызывается с отключёнными хуками, секреты в отчёте маскируются. Если установлен `gitleaks`, история git проверяется через него, иначе — встроенным проходом по `git log -p`.

Что ловит (кратко): секреты по ~27 шаблонам в коде и истории git, закоммиченный `.env`; серверные ключи в `NEXT_PUBLIC_`/`VITE_` (anon- и publishable-ключи — нет); прямые вызовы платных API и service_role в клиентском коде; SQL/NoSQL/command-инъекции, `eval`, небезопасную десериализацию; XSS-синки; AI-эндпоинты без авторизации и `max_tokens`; server actions и мутации без проверки сессии; вебхуки без подписи; rate limit по подделываемому заголовку; IDOR-подозрения; mass assignment; токены в localStorage; JWT без проверки; адресат письма из запроса (open relay); CSV-инъекции; RLS, `using (true)` и `security definer` в миграциях Supabase; CSP с `unsafe-inline`; source maps; устаревший Next.js с обходом middleware; `npm`/`pnpm audit`.

Как читать: 🔴 critical, 🟡 warning, 🔵 «на проверку». Это эвристики — отсюда принцип 7. Ложное срабатывание гасится комментарием `security-audit: ignore` на строке (или `security-audit: ignore-next-line` строкой выше) либо строкой в `.security-audit-ignore` в корне проекта: `rule_id`, `glob` или `glob rule_id`. Ноль находок не значит «безопасно»: логику доступа, живую БД и настройки облачных консолей сканер не видит.

## Live-проверка своего домена (только по просьбе)

```bash
python3 <папка-скилла>/scripts/livecheck.py https://свой-домен
```
Делает пассивные GET-запросы (не больше 18, с паузами): проверяет заголовки и качество CSP, флаги cookies, редирект HTTP→HTTPS, открытые `.env`/`.git`/дампы, публичные source maps, stack trace на странице ошибки и служебные пути в robots.txt. Скрипт сам спрашивает подтверждение владения. Флаг `--yes-i-own-this` ставь только после явного «да, это мой домен». Чужие домены — никогда.

## Если найден живой ключ
1. Перевыпусти ключ в консоли сервиса прямо сейчас. Ключ, побывавший в git, скомпрометирован, даже если репозиторий приватный.
2. Перенеси его в переменные окружения или секрет-менеджер, а `.env*` добавь в `.gitignore`.
3. Историю почисти `git filter-repo` — после перевыпуска, а не вместо него.

## Честные ограничения
Это структурированный аудит силами ИИ, а не пентест и не гарантия. Для прода с деньгами и персональными данными стоит хотя бы раз позвать живого специалиста. Это говоришь в конце отчёта один раз, без запугивания.
