# Чек-лист полного аудита

Для каждого раздела: найди опасные паттерны, проверь наличие защиты, оцени риск. Статус раздела: **найдена проблема / защищено / неприменимо** (с обоснованием) / **не проверено** (с причиной). «Защищено» ставится только после проверки запуском (`dynamic-testing.md`).

Контекст из реального инцидента (сервис Calorize): бот начал атаку через **16 секунд** после появления формы в сети. Сначала SQL-инъекция в поле «имя», затем перебор XSS: тег с `onerror`, `svg` с `onload`, выход из строки через кавычку. Выводы: любая публичная форма атакуема с первого дня; бот перебирает все контексты подряд (SQL, HTML-тело, атрибут, JS-строка, URL); stored XSS чаще срабатывает не на публичной странице, а в админке, CRM или письме, где владелец открывает заявку.

## 1. SQL / NoSQL-инъекции
**Искать:**
- склейку строк или шаблонные литералы с вводом внутри SQL;
- сырые запросы: `$queryRawUnsafe`, `$executeRawUnsafe`, `sql.raw`, `sql.unsafe`, `knex.raw`, `connection.query` со строкой, `sequelize.query` без replacements; в Python — f-строки и `%` в `execute`; в JVM — конкатенацию в `createNativeQuery`/`Statement`, `s"..."` в Scala;
- динамические `ORDER BY`, имена колонок и таблиц, `LIMIT`, `IN (...)` из ввода — параметризация их не закрывает, нужен whitelist;
- NoSQL: объект из `req.body` целиком в фильтре (операторы `$ne`, `$gt`, `$where`, `$regex`);
- `LIKE` без экранирования `%` и `_`;
- в Supabase: `.rpc()` с функциями, которые внутри собирают SQL через `format()`/`EXECUTE` без `%L`/`%I`.

**Достаточно, если:** все запросы параметризованы или идут через ORM без raw-методов; динамические идентификаторы проходят whitelist; ввод для NoSQL приводится к ожидаемому типу.

## 2. XSS во всех контекстах
Каждый контекст, куда попадают пользовательские данные, проверяется отдельно:

| Контекст | Что искать |
|---|---|
| HTML-тело | `dangerouslySetInnerHTML`, `innerHTML`, `outerHTML`, `insertAdjacentHTML`, `document.write`, `v-html`, `{@html}`, неэкранированный вывод шаблонизаторов (`{{{ }}}`, `\|safe`, `<%- %>`, `th:utext`) |
| HTML-атрибут | ручная сборка HTML-строк с атрибутами, особенно без кавычек; spread пользовательского объекта в props (`{...userProps}` даёт `on*`-обработчики или `dangerouslySetInnerHTML`) |
| JS-строка | ввод внутри `<script>`, inline-скриптов, `next/script`, `eval`, `new Function`, `setTimeout(string)`; `JSON.stringify` внутри `<script>` без экранирования `<` |
| URL | ввод в `href`, `src`, `action`, `formAction`, `window.location`, `router.push`: блокируются ли схемы `javascript:`, `data:`, `vbscript:` (частый случай — поле «сайт» в профиле) |
| CSS | ввод в `style`, CSS-переменные, `url()` |
| Markdown / rich text | есть ли санитайзер (DOMPurify, sanitize-html, rehype-sanitize), его конфигурация и версия |
| SVG | загрузка и показ SVG от пользователя (может содержать скрипты и обработчики) |
| Метаданные | ввод в `<title>`, meta, OpenGraph, JSON-LD |

**Stored XSS в «тихих» местах — проверить обязательно:**
- админка/CRM: как отображаются имена, комментарии, описания заявок;
- HTML-письма: экранируется ли ввод при подстановке;
- уведомления в мессенджеры с HTML/Markdown-разметкой;
- логи, которые показываются в админке;
- экспорт в CSV/Excel: formula injection (значения, начинающиеся с `=`, `+`, `-`, `@`).

**DOM-based XSS:** чтение `location.hash`, `location.search`, `document.referrer`, данных `postMessage` без проверки `origin` с последующей записью в DOM.

**Достаточно, если:** вывод идёт через автоэкранирование фреймворка; каждый обход экранирования использует санитайзер актуальной версии; URL проходят проверку схемы; письма и уведомления экранируют ввод.

## 3. CSP и заголовки безопасности
Найди, где задаются заголовки: `next.config.js` → `headers()`, `middleware.ts`/`proxy.ts`, `netlify.toml`, `_headers`, `vercel.json`, конфиг веб-сервера, `helmet()`. Проверь:
- CSP есть; в `script-src` нет `unsafe-inline`/`unsafe-eval`, либо используются nonce/hash (при nonce `unsafe-inline` игнорируется браузером — это нормально);
- `object-src 'none'`, `base-uri 'self'`, `frame-ancestors`;
- `X-Content-Type-Options: nosniff`, `Referrer-Policy`, `Strict-Transport-Security`, `Permissions-Policy`;
- CSP не в режиме Report-Only (он ничего не блокирует).

**Главное:** погасит ли текущая CSP инъекцию обработчика `onerror`/`onload`, если экранирование где-то пропущено. Это проверяется только в браузере (`dynamic-testing.md`, рецепт 2) — по тексту политики легко ошибиться.

## 4. Сессии, cookies, аутентификация
- Флаги сессионных cookies: `HttpOnly`, `Secure`, `SameSite` (Lax/Strict).
- Токены в `localStorage`/`sessionStorage` (доступны любому XSS).
- Хеширование паролей: bcrypt/argon2/scrypt, а не MD5/SHA без соли.
- Защита от перебора паролей и OTP: лимиты попыток, блокировка.
- Сброс пароля: одноразовые токены с истечением срока; ответ не раскрывает, существует ли аккаунт.
- Инвалидация сессий при выходе и смене пароля.
- JWT: фиксированный список алгоритмов (никакого `none`), проверка подписи и `exp`, секрет не в коде.
- OAuth: проверка `state`, redirect URI без wildcard.

## 5. CSRF
- Мутирующие запросы через GET.
- Проверка `Origin`/`Referer` или CSRF-токены для форм и API с cookie-аутентификацией.
- Server actions: настройка `allowedOrigins` без `*`.
- Небезопасный CORS: `Access-Control-Allow-Origin: *` или отражение любого origin вместе с credentials.

## 6. Валидация ввода
- Серверная валидация (zod, yup, valibot, class-validator, pydantic) на каждой точке ввода, а не только на клиенте.
- Разумные ограничения: формат имени, телефона, email; максимальная длина полей; лимит размера тела запроса.
- Приведение типов: число действительно число, не пришёл массив вместо строки.
- Свободные текстовые поля на маркетплейсах: фильтр контактов (телефоны, мессенджеры, ссылки), если бизнес-модель требует, чтобы сделки шли через платформу.
- **Валидация не заменяет экранирование:** отметь места, где проект полагается только на валидацию.

## 7. Защита от ботов и автоматизации
- Rate limiting на формы, логин, регистрацию, сброс пароля, OTP, отправку сообщений, поиск, AI-вызовы — по IP и/или по аккаунту.
- **По чему ключуется лимит и можно ли это подделать.** Заголовки `X-Forwarded-For`, `X-Real-IP` и подобные клиент может прислать сам. Ключ должен приходить из источника, который выставляет платформа (см. `stacks/hosting.md`). Проверяется только запуском.
- Где хранится счётчик: in-memory `Map` в serverless обнуляется на каждом холодном старте и не делится между инстансами — фактически лимита нет.
- Капча или honeypot на публичных формах; защита от массовой регистрации и спама заявками.

## 8. Загрузка файлов
- Тип проверяется по содержимому (magic bytes), а не только по расширению или `Content-Type` клиента.
- SVG и HTML запрещены или санитизированы.
- Есть лимит размера (на сервере и в политике хранилища).
- Имена файлов: защита от path traversal (`../`), генерация своих имён.
- Отдача файлов: с отдельного домена или с `Content-Disposition: attachment` для небезопасных типов; приватные файлы — через подписанные URL с коротким сроком.

## 9. Авторизация и доступ к объектам (IDOR)
- На сервере проверяется, что пользователь владеет объектом, который читает или меняет (заявка, профиль, заказ, файл, сообщение). Проверяется двумя аккаунтами.
- Маршруты админки/CRM защищены на сервере — и в middleware, и в самих handler'ах/actions, а не только скрытием в UI. `noindex` и `Disallow` в robots.txt — не защита: robots.txt публичный и подсказывает пути.
- Mass assignment: можно ли передать в запросе `role`, `isAdmin`, `price`, `userId`, `status`, `balance`.
- В Supabase авторизация — это RLS: у каждой таблицы, каждой операции (select/insert/update/delete) своя политика, `with check` на запись.

## 10. SSRF и open redirect
- Серверный `fetch` по URL из ввода (превью ссылок, импорт по URL, вебхуки): whitelist, блок внутренних адресов (включая 169.254.169.254) после DNS-резолва, без следования редиректам.
- Редиректы по параметрам `redirect`, `next`, `returnUrl`, `callbackUrl`: только относительные пути (не `//` и не `/\`) или whitelist доменов.

## 11. Секреты и утечки информации
- Секреты в репозитории, в том числе в истории git и в случайно закоммиченных `.env*`.
- Серверные ключи с префиксом `NEXT_PUBLIC_`/`VITE_` или в клиентском бандле: поиск по `.next/static` после сборки.
- Подробные ошибки и stack trace в ответах API и на страницах 404/500 в продакшене; тексты ошибок БД/SDK в ответах edge-функций.
- Лишние поля в ответах API: хеши паролей, email других пользователей, внутренние ID; `select('*')` на публичных страницах.
- Открытые source maps в продакшене.

## 12. Зависимости
- Результат `npm audit`/`pnpm audit`/`pip-audit` — критичные и высокие уязвимости.
- Устаревшие версии фреймворка с известными CVE (в Next.js — обход middleware и RCE в React Server Components; см. `stacks/nextjs.md`).
- Версии санитайзеров и библиотек рендера markdown.
- Lock-файл в репозитории; подозрительные `postinstall`-скрипты в новых пакетах.

## 13. Обнаружение атак и логирование
В инциденте атаку заметили именно по логам. Проверь:
- логируются ли отклонённые и подозрительные запросы: ошибки валидации, срабатывания rate limit, неудачные логины, неверные подписи вебхуков;
- не пишутся ли в логи пароли, токены, полные персональные данные;
- можно ли по логам восстановить, что отправлял атакующий: IP, время, маршрут, поле;
- есть ли алерты или хотя бы место, где владелец это увидит;
- не выводятся ли логи в админке без экранирования (XSS через логи).

## 14. Деньги, бизнес-логика, расходы на AI
- **Цена и сумма считаются на сервере.** Клиент присылает id товара и количество, но не цену, скидку и не итог.
- **Гонки (race conditions):** выплаты, списания, промокоды, лимиты «один раз на пользователя». Два одновременных запроса не должны пройти оба: нужны атомарный `UPDATE ... WHERE status = 'pending'` с проверкой числа затронутых строк, уникальные ограничения, `SELECT ... FOR UPDATE` или advisory lock.
- **Идемпотентность:** повторный вебхук или двойной клик не создаёт второй платёж или выплату (idempotency key, уникальный индекс по id события).
- **Вебхуки платёжек** проверяют подпись по сырому телу; статус «оплачено» ставит только вебхук, а не редирект с `?success=true`.
- **Переходы статусов** (escrow, заказ, выплата) разрешены только в правильном порядке и только нужной роли.
- **AI cost bomb:** эндпоинты с LLM закрыты авторизацией, есть лимит на пользователя, `max_tokens`, лимит длины входа и дневной бюджет или алерт в консоли провайдера.

## 15. Инфраструктура и конфиги
- БД не торчит в интернет: порты в docker-compose, `0.0.0.0`, публичные инстансы.
- Нет дефолтных паролей (`postgres`/`root`/`admin`).
- Debug-режим выключен в проде (`DEBUG=True`, `app.run(debug=True)`).
- Секреты не запекаются в Docker-образ (`ENV` с ключами).
- GitHub Actions: пользовательский текст не подставляется через `${{ }}` прямо в `run:`; `pull_request_target` не собирает код из чужого PR.
- Переменные окружения на хостинге разделены по окружениям (preview не получает прод-ключи).
