# Проверка запуском

Правило: утверждение «защищено» требует наблюдаемого результата — кода ответа, строки лога или сообщения браузера. Каждую проверку записывай так:

```
Проверка: <что проверяем>
Команда: <точная команда или действие в браузере>
Наблюдение: <что увидели — код, фрагмент ответа, строка лога/консоли>
Вывод: защищено / найдена проблема / не проверено (почему)
```

Всё локально, со своими тестовыми аккаунтами и тестовыми ключами. Прод, чужие серверы и боевые ключи не трогаем. Маркеры безвредные: `<b>audit-marker</b>`, `'`, `"`, `<`, `>`, `&`.

## 0. Подготовка
1. Поставь зависимости: `npm ci` (или `pnpm i --frozen-lockfile`, `pip install -r requirements.txt`).
2. Окружение — только тестовое: `.env.local` с тестовыми ключами (Stripe test mode, отдельный проект Supabase или локальный `supabase start`, тестовый домен почты). Если под рукой только боевые ключи — остановись и скажи об этом пользователю.
3. Для ошибок, заголовков и CSP нужна **прод-сборка**: `npm run build && npm run start`. Dev-режим показывает подробные ошибки и часто ставит другие заголовки, поэтому выводы по нему неверны.
4. Заведи аккаунты: A (обычный), B (обычный), admin — если есть роли.
5. Ниже `BASE=http://localhost:3000`. В Git Bash на Windows curl работает так же. Если в ответах кракозябры, добавь `| iconv -f utf-8` или смотри через `-o file`.

## 1. Экранирование во всех местах вывода
1. Отправь маркер в каждое текстовое поле каждой формы, включая имя, комментарий и «о себе»:
   `<b>audit-marker</b> ' " < > &`
2. Открой **все** места, где это выводится: публичную страницу, профиль, админку/CRM, письмо, уведомление в Telegram, экспорт.
3. Смотри исходный HTML, а не отрисованную страницу:
   ```bash
   curl -s "$BASE/profile/123" | grep -o 'audit-marker.\{0,40\}'
   ```
   Защищено, если видно `&lt;b&gt;audit-marker&lt;/b&gt;`, `&#x27;`/`&quot;`. Проблема, если видно `<b>audit-marker</b>` как тег или жирный текст на странице.
4. **Письма:** перехвати HTML письма (Mailpit/MailHog локально, лог отправки, тестовый режим провайдера) и ищи тот же маркер.
5. **Telegram/Slack:** при `parse_mode: HTML` маркер должен прийти как текст `<b>…`, а не жирным. Ошибка API «can't parse entities» — тоже находка: сломанное экранирование.
6. **Атрибуты и URL:** в поле «сайт»/«ссылка» введи `javascript:alert(1)`. Это не исполняется, пока никто не кликнет. Проверь, что значение отклоняется валидацией или в `href` не попадает схема `javascript:`.
7. **CSV-экспорт:** значение `=1+1` в имени после выгрузки должно начинаться с апострофа (`'=1+1`).

## 2. CSP на практике
Текст политики легко прочитать неверно. Проверяй в браузере.
1. Прод-сборка локально, открой страницу, DevTools → Console.
2. Сымитируй пропущенное экранирование. Это единственный исполняемый маркер в методике: только локально, он только пишет строку в консоль. Выполни в консоли:
   ```js
   document.body.insertAdjacentHTML('beforeend', '<img src="/nonexistent.png" onerror="console.log(\'csp-audit-marker\')">')
   ```
3. Результат:
   - **Защищено:** в консоли ошибка вида «Refused to execute inline event handler because it violates the following Content Security Policy directive…», а строки `csp-audit-marker` нет.
   - **Проблема:** в консоли напечаталось `csp-audit-marker` — CSP не гасит инъекцию обработчика.
4. Тот же тест повтори на странице, куда выводится пользовательский контент (профиль, админка): у разных маршрутов могут быть разные заголовки.
5. Заголовки прод-сборки:
   ```bash
   curl -sI "$BASE/" | grep -iE 'content-security|strict-transport|x-content-type|referrer-policy|permissions-policy|x-frame'
   ```

## 3. Rate limit и по чему он ключуется
1. Узнай лимит из кода (например, 5 в час). Отправь N+2 запроса:
   ```bash
   for i in $(seq 1 7); do curl -s -o /dev/null -w "%{http_code} " -X POST "$BASE/api/contact" \
     -H 'Content-Type: application/json' -d '{"name":"audit-marker","email":"a@example.com","message":"x"}'; done; echo
   ```
   Ожидание: последние ответы — `429`.
2. Главная проверка — тот же цикл, но с меняющимся заголовком:
   ```bash
   for i in $(seq 1 7); do curl -s -o /dev/null -w "%{http_code} " -X POST "$BASE/api/contact" \
     -H "X-Forwarded-For: 10.0.0.$i" -H "X-Real-IP: 10.0.0.$i" -H "CF-Connecting-IP: 10.0.0.$i" \
     -H 'Content-Type: application/json' -d '{"name":"audit-marker","email":"a@example.com","message":"x"}'; done; echo
   ```
   Если все ответы `200` — лимитер ключуется по заголовку от клиента, и защиты нет.
3. Локально платформенных заголовков нет, поэтому поведение на хостинге может отличаться. Прочитай, откуда код берёт IP, и сверь со `stacks/hosting.md`. Проверка на preview-деплое — это уже запросы к хостингу: только со своего preview и после согласия пользователя.
4. Serverless: если счётчик хранится в памяти (`new Map()`), лимит сбрасывается между инстансами. Это находка даже при пройденном локальном тесте.

## 4. IDOR — два аккаунта
1. Под A создай объект (заявку, заказ, файл) и запиши его id.
2. Под B запроси, измени и удали его:
   ```bash
   curl -s -o /dev/null -w "%{http_code}\n" "$BASE/api/orders/$ID" -H "Cookie: $COOKIE_B"
   curl -s -o /dev/null -w "%{http_code}\n" -X PATCH "$BASE/api/orders/$ID" -H "Cookie: $COOKIE_B" \
     -H 'Content-Type: application/json' -d '{"note":"audit-marker"}'
   ```
   Ожидание: `403` или `404`, и в БД ничего не изменилось. Проверь БД — некоторые API отвечают 200 и молча ничего не делают.
3. Supabase напрямую (минуя API проекта) — под сессией B через anon key:
   ```bash
   curl -s "$SUPABASE_URL/rest/v1/orders?id=eq.$ID" -H "apikey: $ANON_KEY" -H "Authorization: Bearer $JWT_B"
   ```
   Ожидание: `[]`. Затем то же без `Authorization` (гость).
4. Server actions вызываются напрямую так же: из DevTools → Network скопируй запрос action как cURL и повтори его с cookie B.

## 5. Mass assignment
Отправь в обновление профиля или заказа лишние поля: `role`, `is_admin`, `price`, `user_id`, `status`, `balance`. Затем прочитай объект из БД. Защищено, если поля не изменились.

## 6. CSRF и CORS
```bash
curl -s -o /dev/null -w "%{http_code}\n" -X POST "$BASE/api/profile" -H "Origin: https://evil.example" \
  -H "Cookie: $COOKIE_A" -H 'Content-Type: application/json' -d '{"name":"audit-marker"}'
curl -sI "$BASE/api/profile" -H "Origin: https://evil.example" | grep -i access-control
```
Ожидание: мутация с чужим Origin отклонена, `Access-Control-Allow-Origin` не отражает чужой домен вместе с `Allow-Credentials: true`. Отдельно проверь, нет ли мутаций через GET.

## 7. SQL и валидация
- Кавычка в каждое поле (`O'Brien "audit-marker"`): ответ не `500`, в логах нет синтаксической ошибки SQL, значение сохранилось как текст.
- Типы: массив вместо строки (`{"name":["a"]}`), объект с оператором (`{"email":{"$ne":null}}`), строка вместо числа — ответ `400`, а не `500` и не успех.
- Длина и размер: поле на 100 000 символов и тело на 2 МБ — ответ `400`/`413`.

## 8. Утечка ошибок
На прод-сборке сломай запрос: невалидный JSON, несуществующий id, неверный тип. В ответе не должно быть stack trace, путей к файлам, текста ошибок БД/SDK. Для edge-функций Supabase смотри тело ответа при ошибке.

## 9. Загрузка файлов
Загрузи текстовый файл с расширением `.jpg`, файл `.svg`, файл больше лимита и файл с именем `../../audit-marker.txt`. Ожидание: первые три отклонены, имя из четвёртого не используется как путь. Проверь `Content-Type` и `Content-Disposition` при отдаче.

## 10. Open redirect
```bash
curl -s -o /dev/null -w "%{http_code} %{redirect_url}\n" "$BASE/login?next=https://example.com"
curl -s -o /dev/null -w "%{http_code} %{redirect_url}\n" "$BASE/login?next=//example.com"
```
Ожидание: редирект остаётся на своём домене.

## 11. Логи
После прогона всех проверок открой логи. В них должны быть отклонённые запросы (429, 400, 403, неверные подписи) с IP, временем и маршрутом, и не должно быть паролей, токенов и полных персональных данных. Если логов нет — это находка раздела 13.

## Что делать, если запустить нельзя
Нет кода, нет окружения, нужна боевая БД — не додумывай. Такие пункты идут в «Не проверено» с причиной и готовой командой из этого файла, чтобы пользователь мог проверить сам.
