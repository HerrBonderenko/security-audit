# Supabase

## Модель угроз в одной фразе
Anon/publishable ключ **публичный по задумке** — он лежит в браузере, и любой может ходить в REST API базы напрямую, минуя твой фронтенд. Поэтому вся авторизация данных — это **RLS**. Код приложения в этом месте ничего не защищает.

## RLS
- **Каждая** таблица в схеме `public` (и любой схеме, открытой через API) — с `enable row level security`. Сканер сверяет это по миграциям. Живую БД проверь в Dashboard → Advisors → Security Advisor.
- Политика на **каждую операцию**: select / insert / update / delete. Для записи обязательно `with check`, иначе пользователь обновит строку так, что она станет «чужой» (например, подменит `user_id`).
- `using (true)` допустимо только для намеренно публичного чтения (каталог, цены). На запись — никогда.
- Типовое условие: `using ((select auth.uid()) = user_id)`; обёртка в `select` кэширует вызов и ускоряет запросы.
- Колонки, которые пользователь не должен менять (`role`, `balance`, `status`, `price`), нельзя защитить политикой на строку. Используй отдельную таблицу, триггер, отзыв прав на колонку (`revoke update (role) on profiles from authenticated`) или меняй только через серверную функцию.
- Представления (views) по умолчанию обходят RLS: создавай с `security_invoker = true`.

## Ключи
- `service_role` / `sb_secret_…` обходят RLS полностью. Место им — только сервер и edge-функции, никогда с `NEXT_PUBLIC_`.
- Новые ключи `sb_publishable_…` публичные, как anon; `sb_secret_…` — секретные.
- Серверный клиент с service_role должен сам проверять права пользователя: RLS для него не работает.

## Функции и RPC
- `security definer` выполняется с правами владельца (обычно postgres, мимо RLS). Нужен `set search_path = ''` и полные имена (`public.orders`), а внутри — проверка `auth.uid()`.
- Любая функция в `public` вызывается через `/rest/v1/rpc/имя` любым с anon key. Лишние — в приватную схему или `revoke execute ... from anon, authenticated`.
- Динамический SQL внутри функций — только `format('%I', …)` для идентификаторов и `%L` для значений.

## Auth
- Встроенные лимиты: Dashboard → Authentication → Rate Limits. Для sign-up/OTP включи CAPTCHA (Turnstile/hCaptcha).
- Сайт и redirect URLs: без wildcard на чужие домены.
- На сервере пользователя берём через `supabase.auth.getUser()` (или `getClaims()`), который проверяет токен. Не `getSession()` из cookies без проверки.

## Edge Functions
- «Verify JWT» включён для всего, что не является публичным вебхуком. Вебхук без JWT сам проверяет подпись провайдера.
- CORS: не `*`, если функция работает с cookie/сессией; обработчик `OPTIONS`.
- Ответ при ошибке — без `error.message` от БД и SDK. Это частая утечка структуры.
- Секреты — через `supabase secrets set`, не в коде функции.

## Storage
- Политики на `storage.objects` для каждого бакета: кто читает, кто пишет, в какой префикс (`(storage.foldername(name))[1] = auth.uid()::text`).
- Публичный бакет — только для действительно публичных файлов. Приватные отдаются через signed URL с коротким сроком.
- Лимит размера и `allowed_mime_types` в настройках бакета. Загрузка напрямую из браузера — значит, проверки только на стороне Storage.

## Проверка запуском
Два пользователя и прямые запросы к `$SUPABASE_URL/rest/v1/<table>` с anon key: гость, A, B. Рецепт — `dynamic-testing.md`, раздел 4.
